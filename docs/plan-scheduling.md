# 测试计划定时巡检

在测试计划详情的“巡检排期”中填写 Cron、时区、重叠执行和错过触发策略。预览会列出未来五次触发时间，不会保存设置或开始执行。勾选“启用巡检”并保存后，首次从当前时间之后的下一个触发点开始；不会补跑启用之前的历史。

Cron 使用六个字段：秒、分、时、日、月、周。例如 `0 30 9 * * MON-FRI` 表示工作日 09:30。时区为空时采用服务器默认值 `Asia/Shanghai`；夏令时按 Java 时区规则计算。无效 Cron、无效时区及启用时缺少表达式均拒绝保存。

重叠策略 `SKIP` 会跳过已有排队或正在自动执行的同计划运行；`QUEUE` 将触发保存在数据库中，等待前一次结束。手工启动的同计划运行也参与判断。等待人工判定的运行不占用自动执行槽，避免无人确认时阻塞全部后续巡检。默认每个计划最多保留 100 条等待触发，超过上限的触发有单独的跳过记录。

晚到超过 30 秒时，按错过策略 `SKIP` 或 `FIRE_ONCE` 跳过或合并补跑一次。停机期间的全部错过时刻合并成一个区间，不会逐秒回放。轮询略有延迟而跨过多个触发点时也会记录合并区间。实际执行时读取当时的测试资产并保存快照；历史同时保留触发时和派发时的计划版本。

停用、修改排期或删除计划会取消尚未派发的旧触发，已经提交的运行保持其快照及历史。业务字段的普通编辑不会重置排期。派发无法建立有效执行快照时记为“派发失败”，不会自动重放可能有副作用的业务操作。

前端只提交被修改的排期字段，并使用当前资产版本。发生并发冲突时保留草稿，明确选择“保留我的修改并使用最新版本”后再保存。切换详情页签不会清除未保存的排期或计划说明。AI 可以生成表达式和策略，但不能开启排期或群通知；旧的待采纳 AI 候选也在采纳时重新校验这一限制。

数据库的游标和 `(plan_id, scheduled_for)` 唯一约束是触发去重依据。进程轮询只负责唤醒处理，不依赖内存中的最后执行时间。以下服务配置可按容量调整：

```yaml
aitest:
  schedules:
    enabled: true
    default-timezone: Asia/Shanghai
    poll-interval-ms: 1000
    misfire-grace-seconds: 30
    max-queued-per-plan: 100
```

排期使用现有任务队列和三个实际执行器，不引入 Quartz、Kafka 或独立调度服务。触发历史中的“查看运行”打开该次真实运行，是否通过以运行结果为准。
